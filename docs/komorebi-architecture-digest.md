# komorebi Architecture Digest

> Behavioral study of [komorebi](https://github.com/LGUG2Z/komorebi) (source-available under the Komorebi License 2.0.0), produced 2026-08-10 by a multi-agent code-reading pass over the komorebi daemon, CLI, and layout crates. This is a description of observed behavior and Windows API usage for building an independent implementation — komorebi's source is cited by file and line as a factual reference, but none of its code is reproduced here or used in YTile.

## Event capture and processing (WinEvent hook -> channel -> WindowManager::process_event) in komorebi
Capture side: `winevent_listener::start()` (called early in `main()`) spawns a dedicated thread that installs a single global out-of-context accessibility hook via `SetWinEventHook(EVENT_MIN, EVENT_MAX, None, win_event_hook, 0, 0, WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS)` — i.e. it subscribes to the entire WinEvent range for all processes/threads, excluding komorebi's own windows (borders, etc.) to avoid feedback loops. Because WINEVENT_OUTOFCONTEXT hooks are delivered as messages to the installing thread, that same thread must run a Win32 message pump; it immediately enters a `GetMessageW`/`TranslateMessage`/`DispatchMessageW` loop (with an extra, technically unnecessary 10ms sleep per iteration). Without this pump the callback would never fire. The callback `windows_callbacks::win_event_hook` does coarse filtering: it drops anything where `id_object != OBJID_WINDOW` (child/UI-element events), converts the raw u32 to the `WinEvent` enum via `TryFrom` (unknown values dropped), does two border-manager fast paths (forwards ObjectLocationChange/ObjectDestroy directly to the window's border HWND via `SendNotifyMessageW` so borders track moves with low latency, and re-pokes the border manager on SystemForeground because GetForegroundWindow can lag the event), then maps the WinEvent to a semantic `WindowManagerEvent` via `WindowManagerEvent::from_win_event`. Unmapped WinEvents are trace-logged and dropped. The mapping is small: ObjectDestroy->Destroy; ObjectHide->Hide; ObjectCloaked/Uncloaked->Cloak/Uncloak; SystemMinimizeStart->Minimize; ObjectShow|SystemMinimizeEnd->Show; ObjectFocus|SystemForeground->FocusChange; SystemMoveSizeStart/End->MoveResizeStart/End; SystemCaptureStart/End->MouseCapture; ObjectNameChange->Show-or-TitleUpdate (a per-app hack, see gotchas). Mapped events are pushed into a global `OnceLock`-held crossbeam bounded(20) channel (`winevent_listener::event_tx()`); a full channel makes the hook callback block, and a closed one panics via `expect`.

Processing side: the receiver half of the same channel is handed to `WindowManager::new` as `wm.incoming_events`. `process_event::listen_for_events` spawns a consumer thread that loops `receiver.recv()`, takes the global `Arc<Mutex<WindowManager>>` lock, and calls `wm.process_event(event)`, logging errors and continuing. This serializes all window-management mutations through one mutex that is shared with the command socket thread, border/stackbar/transparency/reaper/monitor-reconciliator threads. The same channel is also fed by the WM itself: `komorebic manage/unmanage` inject `Manage`/`Unmanage` events, and the custom focus-follows-mouse thread (`process_movement.rs`, a winput mouse hook loop) injects `Raise` events, so synthetic and OS-originated events flow through one queue.

`process_event` first drops everything while paused, then runs the fine-grained filter `Window::should_manage` (window.rs): must be a real window (`IsWindow`), meet minimum width/height, have a title, pass the cloak check (`DwmGetWindowAttribute` DWMWA_CLOAKED; cloaked windows are only allowed for Hide/Cloak events so cloaked-window removals still process), and pass `window_is_eligible`: not in PERMAIGNORE_CLASSES or user ignore rules (unless force-managed), and style-wise have WS_CAPTION+WS_EX_WINDOWEDGE, not WS_EX_DLGMODALFRAME, and not WS_EX_LAYERED unless whitelisted (layered windows generate duplicate events that cause redraw storms). Then it optionally gates on virtual-desktop identity, updates the focused monitor from FocusChange/Show/MoveResizeEnd coordinates, enforces workspace rules, and dispatches per event type: Destroy/Unmanage -> remove window from focused workspace, retile, refocus only if the OS promoted no foreground successor; Minimize -> remove+retile unless komorebi itself hid the window (HIDDEN_HWNDS) or a display-change is in progress; Hide -> remove only if the window is truly gone or the app is on the tray/multi-window list (many apps send Hide when minimizing or closing to tray); FocusChange -> drop if stale (window is no longer `GetForegroundWindow`), then sync focused container/floating layer; Show/Manage/Uncloak -> alt-tab reconciliation if the hwnd is already known on another workspace/stack, dedup checks against `known_hwnds` and all workspaces to prevent ghost tiles, then insert as floating or into a new/appended container and retile; MoveResizeStart -> record pending (monitor, workspace, hwnd) op; MoveResizeEnd -> compare new rect vs the layout's old rect — zero right/bottom delta means a drag (swap containers at cursor, or transfer across monitors), otherwise a resize translated into layout resize ops; MouseCapture/Cloak/TitleUpdate -> no-op (rules/reaping only). Finally it updates `known_hwnds`, notifies IPC subscribers, and pokes the border/transparency/stackbar managers. There is no time-based debouncing anywhere: "deduplication" is entirely state-based (stale-foreground check, known_hwnds/contains_window membership checks, HIDDEN_HWNDS self-inflicted-event suppression, pending_move_op hwnd matching, uncloack_to_ignore counter), plus the coarse OBJID_WINDOW/style filters that discard the vast majority of the firehose before it reaches the channel. A separate 20ms polling "reaper" thread backstops missed Destroy events by removing hwnds that no longer pass `IsWindow`/`IsWindowVisible`.
Windows APIs: SetWinEventHook (Accessibility) — single global hook over EVENT_MIN..EVENT_MAX with WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS; the sole source of window lifecycle/focus/move notifications; GetMessageW / TranslateMessage / DispatchMessageW — message pump on the hook-installing thread, required for WINEVENT_OUTOFCONTEXT hook delivery; SendNotifyMessageW — hook callback forwards ObjectLocationChange/ObjectDestroy raw events straight to the tracked window's border HWND (border follows window without a round-trip through the WM); GetWindowLongW (GWL_STYLE / GWL_EXSTYLE) — filtering WS_CHILD, WS_EX_TOOLWINDOW, WS_EX_NOACTIVATE in the callback; full style/exstyle eligibility rules (WS_CAPTION, WS_EX_WINDOWEDGE, WS_EX_DLGMODALFRAME, WS_EX_LAYERED) in window_is_eligible; GetForegroundWindow (via WindowsApi::foreground_window) — stale FocusChange rejection and post-Destroy refocus decision; IsWindow / IsWindowVisible / IsIconic / IsZoomed — validity checks in enum callbacks, should_manage, and the reaper's orphan detection; EnumWindows (via enum_window / alt_tab_windows extern callbacks) — initial workspace population and alt-tab candidate listing; GetWindowRect (via WindowsApi::window_rect) — minimum-size filtering and MoveResizeEnd move-vs-resize delta computation; DwmGetWindowAttribute DWMWA_CLOAKED (via window.is_cloaked) — excluding cloaked (e.g. other-virtual-desktop / UWP suspended) windows from management except on Hide/Cloak events; AllowSetForegroundWindow + SystemParametersInfo foreground lock timeout (WindowsApi::foreground_lock_timeout) — startup permission to steal focus later; SetProcessDpiAwarenessContext — DPI awareness so window rects are in physical pixels; OBJID_WINDOW constant — callback discards accessibility events for non-window objects (menus, carets, child UI elements); winput low-level mouse message loop (process_movement) — synthesizes Raise events for the custom focus-follows-mouse implementation
Mechanisms: Dedicated hook thread: winevent_listener::start() spawns one thread that both installs the hook and pumps messages; hook handle/thread stored in a OnceLock so it is started exactly once; Global static crossbeam bounded(20) channel in a OnceLock; event_tx()/event_rx() clone the halves. Producer = hook callback (plus WM-synthesized Manage/Unmanage/Raise events); consumer = single event-processing thread; Two-stage filtering: cheap coarse filter in the hook callback (OBJID_WINDOW, WinEvent enum TryFrom, from_win_event mapping returning None for ~90% of event types) keeps the channel small; expensive rule-based should_manage/window_is_eligible filtering runs on the consumer side under the WM lock; Typed event translation: raw u32 WinEvent -> WinEvent enum (winevent.rs, #[repr(u32)] with exhaustive TryFrom) -> semantic WindowManagerEvent enum carrying the source WinEvent plus a Copy Window{hwnd} struct; Single-mutex actor model: Arc<Mutex<WindowManager>> shared by the event thread, command socket thread, and all manager threads (border, stackbar, transparency, reaper, monitor reconciliator, focus manager); process_event holds the lock for the whole handling of one event, so events are strictly serialized; State-based dedup instead of debouncing: known_hwnds map (hwnd -> (monitor, workspace)), workspace contains_window checks, HIDDEN_HWNDS set for self-initiated hides, pending_move_op tuple for pairing MoveResizeStart/End, has_pending_raise_op flag, uncloack_to_ignore counter, and a stale-focus check comparing event hwnd against GetForegroundWindow; Alt-tab reconciliation: on Show/Uncloak of an hwnd already tracked on another monitor/workspace (or unfocused in a stack), focus is re-pointed to that workspace/container instead of re-adding the window; Reaper backstop: a 20ms polling thread diffs known hwnds against IsWindow/IsWindowVisible and pushes orphan batches over its own channel for removal — covers Destroy/Hide events that never arrive; Border fast path: raw event forwarding from the hook callback to border windows via SendNotifyMessageW, bypassing the WM channel entirely for move-tracking latency; Post-event fan-out: after each processed event the WM notifies IPC subscribers (serialized state diff) and pokes border/transparency/stackbar manager channels via non-blocking try_send (dropped when full)
Gotchas: Firefox (and similar) never send ObjectCreate/ObjectShow on launch — only ObjectNameChange + ObjectLocationChange. from_win_event therefore promotes ObjectNameChange to a Show event for exes on the OBJECT_NAME_CHANGE_ON_LAUNCH list, with a title-regex ignore list on top, and skips minimized windows (Firefox fires NameChange when YouTube autoplay changes the title, issue #941); Many apps send ObjectHide when minimizing or 'closing to tray' while the process stays alive and IsWindow stays true — Hide only removes the window if !is_window() OR the app matches TRAY_AND_MULTI_WINDOW_IDENTIFIERS, and never if komorebi itself hid it (HIDDEN_HWNDS); SystemForeground can fire before GetForegroundWindow reflects the new foreground window, so border focus colors were painted stale — the callback fires an extra border_manager notification for SystemForeground to repaint once the OS catches up; FocusChange events can be stale by the time they are processed — should_skip_focus_change drops them if the event hwnd is no longer the actual foreground window; After destroying a managed window, Windows sometimes promotes no foreground successor (foreground is null) — should_refocus_after_destroy refocuses the surviving selection only in that case, otherwise it defers to the incoming FocusChange to avoid fighting the OS; OleMainThreadWndClass (explorer.exe's hidden OLEChannelWnd COM support window) is always tied to the primary monitor; if it triggers monitor reconciliation the focused monitor index gets stuck at 0 — its class is explicitly excluded from focused-monitor updates; Firefox fires an extra Show when focused during a workspace switch, associating it with both workspaces and creating ghost tiles — process_event checks known_hwnds and every workspace before adding, and hides the window if it belongs to a non-focused workspace elsewhere; Windows fires SystemMinimizeStart for windows on a monitor that briefly disconnects/reconnects — minimizes are ignored while a display change is in progress (10s window) so the monitor reconciliator can restore the layout; WS_EX_LAYERED windows are excluded because they generate duplicate events that send redrawing haywire on FocusChange — but a layered whitelist exists because apps like Steam legitimately need it; WINWORD.EXE keeps an invisible WS_EX_LAYERED window alive after closing one of several docs — the reaper treats non-visible windows as orphans as a hack (disabled under HidingBehaviour::Hide since legitimately hidden windows would be yeeted); the source comment next to it vents at the Office 365 team in memorable terms; Some windows send FocusChange before Show; on an empty workspace komorebi focuses the desktop on the FocusChange, so after adding the first window of a workspace it explicitly re-focuses that window; SLOW_APPLICATION_IDENTIFIERS: some apps report styles/state late, so eligibility checking sleeps a configurable compensation time before evaluating them; JetBrains IDEs spam OBJECT_NAMECHANGE — processed Show(ObjectNameChange) events are logged at trace instead of info to keep logs usable; MoveResizeEnd distinguishes a drag from a resize purely by rect deltas (right/bottom delta == 0 means move); a leftover BORDER_WIDTH+BORDER_OFFSET constant is consulted for resize edge detection with a 'TODO: Determine if this is still needed'; The hook callback blocks on a bounded(20) channel send and panics (expect) if the channel is closed; the message pump loop also sleeps 10ms per message even though GetMessageW already blocks; should_manage only allows cloaked windows through for Hide/Cloak events, so windows on other virtual desktops still get removed but never get managed; Hide events are also always allowed through the layered-transparency gate to avoid ghost tiles; WINEVENT_SKIPOWNPROCESS is load-bearing: without it komorebi's own border/stackbar windows would generate events and feedback loops; MouseCapture (SystemCaptureStart/End) events are consumed only to trigger workspace-rule enforcement and are otherwise explicitly no-ops
Minimal-WM essentials: Essential: (1) a dedicated thread that calls SetWinEventHook with WINEVENT_OUTOFCONTEXT | WINEVENT_SKIPOWNPROCESS and then runs a GetMessageW message pump — without the pump the callback never fires; hooking the full EVENT_MIN..EVENT_MAX range is not required, a minimal WM can register only the handful it consumes (OBJECT_SHOW/HIDE/DESTROY/CLOAKED/UNCLOAKED/FOCUS, SYSTEM_FOREGROUND, SYSTEM_MINIMIZESTART/END, SYSTEM_MOVESIZESTART/END) or install a few narrow hooks; (2) the OBJID_WINDOW filter in the callback — non-window accessibility events dominate the firehose; (3) a channel handing events from the hook thread to a single WM thread that serializes all state mutation (never do layout work inside the hook callback: it runs on the message pump thread and blocking it delays all further events); (4) an eligibility filter equivalent to should_manage's core: IsWindow + visible + has title + not cloaked + style check (WS_CAPTION/WS_EX_WINDOWEDGE present, WS_EX_TOOLWINDOW/WS_EX_NOACTIVATE/WS_CHILD/WS_EX_DLGMODALFRAME absent, layered excluded) plus minimum size — without this you will try to tile tooltips, IME windows, and shell internals; (5) handlers for Show (insert + retile), Destroy/Hide/Minimize (remove + retile), FocusChange (update focused tile, with the stale-foreground check to avoid focus loops), and MoveResizeStart/End (drag-to-swap or ignore); (6) membership dedup against a known-hwnds map, since Windows delivers overlapping Show/Foreground/NameChange bursts for one logical appearance; (7) an initial EnumWindows pass to adopt existing windows. Strongly recommended though not strictly minimal: the ObjectNameChange-as-Show hack (without it Firefox-class apps are simply never tiled) and a reaper-style liveness poll (without it missed Destroy events leave permanent ghost tiles). Optional polish: border/stackbar/transparency managers and their fast-path event forwarding, alt-tab stack reconciliation, virtual-desktop gating, monitor reconciliation and display-change minimize suppression, focus-follows-mouse Raise synthesis, tray/multi-window and slow-application app-specific lists, IPC subscriber notifications, and state dump/restore.

## Windows API surface (windows_api.rs, set_window_position.rs, com/, window.rs, plus winevent/border/monitor/ghost helpers)
komorebi funnels nearly all OS interaction through a single stateless facade, `WindowsApi` in komorebi/src/windows_api.rs, which wraps raw `windows`-crate calls in eyre Results (macros convert 0/NULL returns into `last_os_error`). The core tiling loop is: a WinEvent hook (SetWinEventHook, EVENT_MIN..EVENT_MAX, WINEVENT_OUTOFCONTEXT|WINEVENT_SKIPOWNPROCESS, on a dedicated thread with a GetMessageW pump) turns shell events (show/hide/cloak/destroy/foreground/minimize/movesize) into channel messages; window eligibility is decided by inspecting HWND properties (GetWindowTextW, RealGetWindowClassW, GWL_STYLE/GWL_EXSTYLE via GetWindowLongPtrW, DwmGetWindowAttribute DWMWA_CLOAKED, plus exe name via OpenProcess/QueryFullProcessImageNameW); and layout is applied with SetWindowPos (flags modeled as a bitflags type in set_window_position.rs) after correcting every rect by a "shadow rect" — the delta between GetWindowRect (outer bounds incl. invisible DWM drop shadow) and DWMWA_EXTENDED_FRAME_BOUNDS (painted region) — so tiles visually touch. Focus changes use the classic foreground-lock bypass: SendInput of a dummy mouse event to the WM's own process, SetWindowPos(HWND_TOP), then SetForegroundWindow; startup additionally calls AllowSetForegroundWindow and zeroes SPI_SETFOREGROUNDLOCKTIMEOUT.

Monitors come from two sources: plain Win32 (EnumDisplayMonitors, MonitorFromWindow/MonitorFromPoint with MONITOR_DEFAULTTONEAREST, GetMonitorInfoW for work areas, GetDpiForMonitor MDT_EFFECTIVE_DPI) and the external `win32-display-data` crate (LGUG2Z's wrapper over the DisplayConfig APIs) which supplies stable device paths and serial-number IDs for monitor identity across hotplug. A hidden message-only-style window (monitor_reconciliator/hidden.rs) subscribes to WM_DEVICECHANGE (RegisterDeviceNotificationW for monitor/display-adapter/video-output interface GUIDs), WM_DISPLAYCHANGE, WM_SETTINGCHANGE(SPI_SETWORKAREA), WM_POWERBROADCAST (lid switch via RegisterPowerSettingNotification), and WM_WTSSESSION_CHANGE (WTSRegisterSessionNotification) to drive monitor reconciliation. The process declares DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2 at startup.

COM usage is small but notable. Documented: IDesktopWallpaper (CoCreateInstance of DesktopWallpaper) for per-monitor wallpaper. Undocumented: com/interfaces.rs hand-transcribes (from Ciantic/AltTabAccessor) the internal shell interfaces — CLSID_ImmersiveShell → IServiceProvider::QueryService → IApplicationViewCollection (IID 1841c6d7-4f9d-42c0-af41-8747538f10e5) → get_view_for_hwnd → IApplicationView (IID 372E1D3B-38D3-42E4-A15B-8AB2B178F513), whose vtable includes dozens of methods (many literally named unknown1..12) just to reach `SetCloak`. This is the only way to cloak *foreign* windows (used for workspace switching with HidingBehaviour::Cloak and for hiding a window behind a DWM-thumbnail "ghost" during movement animations), because the documented DwmSetWindowAttribute(DWMWA_CLOAK) returns E_ACCESSDENIED for HWNDs you don't own. Notably absent from this snapshot: IVirtualDesktopManager, AttachThreadInput, and any direct SetWindowsHookEx (the optional "komorebi" focus-follows-mouse implementation gets mouse movement through the `winput` crate's message loop, which installs low-level hooks internally).

Visual chrome is separate machinery: border windows are WS_POPUP + WS_EX_TOOLWINDOW|WS_EX_TOPMOST|WS_EX_NOACTIVATE windows rendered with Direct2D (ID2D1Factory → CreateHwndRenderTarget → DrawRoundedRectangle) on their own message-loop threads, kept in sync with tracked windows by forwarding EVENT_OBJECT_LOCATIONCHANGE/DESTROY from the WinEvent callback via SendNotifyMessageW; stackbars use classic GDI (DrawTextW, RoundRect, fonts); movement animations use DWM live thumbnails (DwmRegisterThumbnail/DwmUpdateThumbnailProperties/DwmFlush) hosted in a click-through WS_EX_TRANSPARENT ghost window while the real window is cloaked.

Mechanisms: Single stateless facade struct (WindowsApi) wrapping every Win32 call; macros convert 0/NULL returns to Result via std::io::Error::last_os_error; HWNDs stored as plain isize everywhere for Send/Sync and serde; Event-driven core: SetWinEventHook callback → WinEvent enum → crossbeam bounded channel → window-manager event loop thread; hook thread runs its own GetMessageW pump (required for WINEVENT_OUTOFCONTEXT delivery); Heavy thread-per-window-class model: each border window, the ghost owner, the stackbar, the hidden monitor-listener window each own a dedicated thread with its own message loop, because HWNDs have thread affinity; cross-thread work is handed over via PostMessageW with WM_USER messages (including Box::into_raw ownership transfer in WM_ANIMATE_RECT); Shadow-rect compensation: every positioning call computes GetWindowRect minus DWMWA_EXTENDED_FRAME_BOUNDS and offsets the target rect so the painted region (not the shadow) fills the tile; SetWindowPosition bitflags newtype over SWP_* constants; async-vs-sync window handling behavior globally switchable (SWP_ASYNCWINDOWPOS / ShowWindowAsync) to avoid blocking on hung apps; Window eligibility pipeline (window.rs should_manage/window_is_eligible): is_window → min size → has title → not cloaked (DWMWA_CLOAKED) → title/exe/class/path rules (ignore/manage/float regex identifiers) → style heuristics (CAPTION+WINDOWEDGE, reject DLGMODALFRAME, reject LAYERED unless whitelisted); ## Data model and tiling/layout subsystem of komorebi (WindowManager > Monitor > Workspace > Container > Window hierarchy, Ring structure, komorebi-layouts algorithms, resize deltas, focus/movement, monocle/maximize/float/stack handling, layout-to-SetWindowPos pipeline, and State serialization for IPC)
komorebi models everything as a tree of "Rings": `WindowManager` holds `Ring<Monitor>`, each `Monitor` holds `Ring<Workspace>`, each `Workspace` holds `Ring<Container>`, and each `Container` holds `Ring<Window>`. A `Ring<T>` is just `VecDeque<T> + focused: usize`; a macro (`impl_ring_elements!`) stamps out `xs()/xs_mut()/focused_x()/focused_x_idx()/focused_x_mut()` accessors on each owner. A `Window` is nothing but `{ hwnd: isize }` — all metadata (title, exe, class, rect, styles) is queried live from Win32 on demand. A `Container` is the tiling unit (a "stack" of one or more windows sharing one tile; only the focused window is shown, the rest are hidden/cloaked). A `Workspace` additionally carries three special layers outside the container ring: `monocle_container: Option<Container>` (+ `monocle_container_restore_idx`), `maximized_window: Option<Window>` (+ restore idx), and `floating_windows: Ring<Window>`, plus per-workspace layout config (`layout`, `layout_flip`, `layout_rules` thresholds, paddings), the mutable tiling state (`resize_dimensions: Vec<Option<Rect>>`, `latest_layout: Vec<Rect>`, `tile: bool`), and a `WorkspaceGlobals` struct that the Monitor pushes down (work area, offsets, border width/offset, default paddings) so `Workspace::update()` can run without reaching back up the tree. `WindowManager` also maintains `known_hwnds: HashMap<hwnd, (monitor_idx, workspace_idx)>` as a reverse index, persisted to komorebi.hwnd.json for the reaper.

The heart of tiling is `Workspace::update()` (komorebi/src/workspace.rs): prune empty containers → compute adjusted work area (work_area minus work_area_offset, minus window-based offset when container count <= limit, minus workspace padding) → enforce per-layout resize constraints → apply threshold-based layout/behaviour rules → then branch: monocle container gets the whole padded area via one `set_position`; a maximized window just gets `ShowWindow(SW_MAXIMIZE)`; otherwise `layout.as_boxed_arrangement().calculate(area, len, padding, flip, resize_dimensions, focused_idx, layout_options, latest_layout)` returns `Vec<Rect>` (one rect per container, index-aligned). Each rect then gets border offset/width padding and a stackbar tab-height reservation, and every window in the container is positioned to it (focused ones also get titlebar removal/restore handling). The rects are cached in `latest_layout` (used for cursor hit-testing and by the Scrolling layout to recover scroll position). Layout algorithms live in the separate platform-agnostic `komorebi-layouts` crate behind the `Arrangement` trait: BSP (recursive fibonacci/dwindle split with configurable column/row ratios), Columns, Rows, VerticalStack, RightMainVerticalStack (borrowed from LeftWM), HorizontalStack, UltrawideVerticalStack (center primary, left secondary, right stack), Grid (ported from LeftWM, sqrt-based column count), Scrolling (PaperWM-style horizontal strip, N visible columns, off-screen windows get out-of-area rects, scroll position derived from latest_layout, optional centered focus), and CustomLayout (user JSON/YAML column definitions: one Primary, optional Secondaries with capacity, one trailing Tertiary that absorbs overflow). Resizing is delta-based, not ratio-based: `resize_dimensions[i]` is an `Option<Rect>` of per-edge pixel deltas for container i; `DefaultLayout::resize` adds ±delta to the dragged edge (clamped against the unaltered tile size), `enforce_resize_constraints*` zeroes edges that make no sense per layout (e.g. in BSP even-indexed containers cannot grow bottom, odd cannot grow right; first can never grow left/top), and each layout's `calculate_*_adjustment` converts the per-container deltas into symmetric adjustments of the container and its neighbors (`resize_left/right/top/bottom` split each delta /2 between the two adjacent tiles).

Directional focus/movement is index arithmetic, not geometry (except for floating windows and cross-monitor hops): the `Direction` trait (komorebi-layouts/src/direction.rs) implements `is_valid_direction` + `up/down/left/right_index` per layout (BSP parity tricks, grid neighbor computation, custom-layout column accumulation), with `OperationDirection::flip` remapping the requested direction when the workspace has a `layout_flip`. `focus_container_in_direction`/`move_container_in_direction` first try the in-workspace index; if none, they either wrap to the adjacent workspace (CrossBoundaryBehaviour::Workspace, PaperWM-style, landing on the layout's leftmost/rightmost index via `cross_boundary_edge_index`) or find the adjacent monitor by comparing monitor edge coordinates (`monitor_idx_in_direction`), moving/swapping the container across (MoveBehaviour::Swap/Insert/NoOp) with `Monitor::add_container_with_direction` choosing front/back/at-focus insertion. Monocle and maximize are toggles that physically remove the focused container/window from the ring, park it in the dedicated Option field with a restore index, and reinsert at that exact index on toggle-off (deliberately using plain VecDeque insert/remove rather than the lock-respecting variants). Stacking moves a window from the focused container into a neighbor (`move_window_to_container`), and `Container::load_focused_window` shows the focused stack member and cloaks the rest. Floating windows live per-workspace, are moved/resized by pixel deltas clamped to the monitor work area, and a `WorkspaceLayer` enum (Tiling/Floating) tracks which layer has focus.

The layout-to-OS pipeline is NOT batched: there is no BeginDeferWindowPos/HDWP anywhere — each window gets its own `SetWindowPos` call via `Window::set_position` → `WindowsApi::position_window`, with flags SWP_NOACTIVATE | SWP_NOSENDCHANGING | SWP_NOCOPYBITS | SWP_FRAMECHANGED, plus SWP_NOZORDER unless the window should be raised (HWND_TOP, deliberately never HWND_TOPMOST), plus SWP_ASYNCWINDOWPOS when WindowHandlingBehaviour::Async so a hung app cannot block the WM thread. The target rect is pre-adjusted by the window's DWM drop-shadow margins (`shadow_rect` = GetWindowRect minus DWMWA_EXTENDED_FRAME_BOUNDS) so the visible frame lands exactly on the computed tile, and set_position early-returns when the rect is unchanged. If animations are enabled, the same call instead drives an AnimationEngine dispatcher that lerps rects on a worker thread (legacy MoveWindow per frame, or the ghost-window path using cloaking plus DWM thumbnails). Threading: one `Arc<Mutex<WindowManager>>` shared by the WinEvent listener thread (events via crossbeam channel → process_event), the UDS socket command listener (process_command), and satellite manager threads (border, stackbar, transparency, focus, reaper, monitor reconciliator) that each lock the WM. For IPC, `State::from(&WindowManager)` clones the whole monitor/workspace/container tree (stripping `workspace_config` and transient fields), serde-serializes it (Window serializes as hwnd+title+exe+class+live rect), and is written to komorebi.state.json on exit (reapplied on restart via `apply_state`) and pushed to subscriber sockets by `notify_subscribers` after each event/command, gated by `State::has_been_modified` diffing.

## IPC and CLI (komorebi daemon command socket, komorebic CLI, komorebi-client library, event subscriptions)
Transport: komorebi's primary IPC channel is a Unix domain socket on Windows, via the `uds_windows` crate (Windows has supported AF_UNIX since Win10 1803). The daemon binds `%LOCALAPPDATA%\komorebi\komorebi.sock` at WindowManager::new (window_manager.rs:137-150), deleting any stale socket file first (with a comment noting `Path::exists()` is unreliable on Windows). An optional TCP listener on `0.0.0.0:<port>` can additionally be enabled with `komorebi.exe --tcp-port` (process_command.rs:147-185) for remote control; connections are kept in a global TCP_CONNECTIONS map with 30s keepalive. Named pipes are used only for the legacy event-subscription path, not for commands.

Protocol: messages are the `SocketMessage` enum (komorebi/src/core/mod.rs:63-265, ~187 variants), serialized as serde JSON with adjacent tagging `#[serde(tag = "type", content = "content")]`, e.g. `{"type":"FocusWorkspaceNumber","content":5}`. Commands are newline-delimited JSON: the client writes one JSON object per line; komorebi-client's send_message opens a fresh UnixStream per invocation, writes, and closes (fire-and-forget); send_batch joins many messages with '\n' on one connection; send_query additionally does `shutdown(Write)` then reads the reply to EOF with a 1s timeout. There is deliberately no framing protocol for replies (TODO comment at process_command.rs:2344-2347) — a reply is a whole pretty-printed JSON blob (State, GlobalState, VisibleWindows, Query results, schemas, DebugWindow output) and termination is signalled by socket shutdown. Server side, listen_for_commands (process_command.rs:104-144) spawns a thread that clones the UnixListener, accepts connections, and spawns a thread per client which reads lines, parses with SocketMessage::from_str (serde_json), acquires the WindowManager mutex with try_lock_for(1s), and calls WindowManager::process_command(message, reply) — one giant match statement (~2,100 lines) where each arm mutates the WM or writes a reply to the same stream. While paused, only TogglePause/State/GlobalState/Stop are processed.

CLI mapping: komorebic (komorebic/src/main.rs) is a clap-derive binary with a SubCommand enum of ~170 subcommands (lines 1040-1582). Arg structs are mass-generated by macros (gen_enum_subcommand_args!, gen_target_subcommand_args!, gen_workspace_subcommand_args!, etc.) so a subcommand like `focus left` parses an OperationDirection and maps 1:1 to `send_message(&SocketMessage::FocusWindow(dir))`. Query-style subcommands (state, query, visible-windows, monitor-information, generate-static-config) use print_query -> send_query and print the JSON response. A handful of subcommands never touch the socket: start/stop/kill spawn or kill komorebi.exe, whkd, komorebi-bar, masir via PowerShell scripts (Start-Process/Stop-Process); log tails the daemon's log file in temp; check/quickstart/autostart manage config files and shortcuts. komorebic-no-console is a tiny #![windows_subsystem = "windows"] wrapper that re-execs komorebic.exe with CREATE_NO_WINDOW so hotkey daemons like whkd can invoke it without a console flash — this is the price of the CLI-driven design: every keypress spawns a process.

Event subscriptions: external clients (komorebi-bar, status bars like yasb/zebar) subscribe via two mechanisms. (1) UDS: the subscriber binds its own socket file in the komorebi data dir (komorebi-client::subscribe binds `%LOCALAPPDATA%\komorebi\<name>` then sends AddSubscriberSocket(name)); on every processed command/WM event, notify_subscribers (komorebi/src/lib.rs:355-437) serializes a Notification { event: NotificationEvent (Socket|WindowManager|Monitor|VirtualDesktop), state: full State } to JSON and does a fresh UnixStream::connect + write per subscriber per notification; connect failures mark the subscription stale and remove it. AddSubscriberSocketWithOptions supports filter_state_changes so subscribers only get notifications when the state actually changed (computed by diffing initial_state vs post-command state, with a few override events always delivered). (2) Named pipes (legacy, `komorebic subscribe-pipe`): the subscriber creates `\\.\pipe\<name>` as the pipe server; komorebi connects as a client via miow::pipe::connect (process_command.rs:1985-1993) and keeps the File open, writing newline-delimited JSON notifications; OS errors 2 (FILE_NOT_FOUND) and 232 (ERROR_NO_DATA / pipe closing) trigger unsubscription. Hotwatch (inotify-style file watching) is not IPC: it watches komorebi.json / legacy komorebi.ahk/ps1 for changes (window_manager.rs watch_configuration, static_config.rs:1367-1386) and triggers config reload; komorebi-bar does the same for its own config.
Windows APIs: AF_UNIX Unix domain sockets via uds_windows crate (UnixListener/UnixStream) — the primary command transport and the subscriber-socket event channel; requires Windows 10 1803+; Named pipes (\\.\pipe\<name>) via miow::pipe::connect — komorebi acts as pipe *client* to a subscriber-created pipe server for the legacy event subscription channel; stale pipes detected via raw OS errors 2 (ERROR_FILE_NOT_FOUND) and 232 (ERROR_NO_DATA); std::net::TcpListener + net2::TcpStreamExt::set_keepalive — optional remote-control command channel (--tcp-port); AllowSetForegroundWindow + SystemParametersInfo foreground lock timeout (WindowsApi wrappers, called at daemon startup so IPC-triggered focus changes actually work); ShowWindow(SW_RESTORE) — used directly by komorebic restore-windows / stop fallback to un-hide windows recorded in komorebi.hwnd.json; SetCursorPos/mouse_event style helpers (WindowsApi::center_cursor_in_rect, left_click) — used by the ForceFocus command; PowerShell subprocesses (powershell_script crate) — komorebic start/stop use Start-Process/Stop-Process to manage komorebi.exe, whkd, komorebi-bar, masir; not a Win32 API but the actual process-management mechanism; CreateProcess with CREATE_NO_WINDOW creation flag (komorebic-no-console wrapper) so hotkey daemons can run CLI commands without console windows flashing
Mechanisms: Single SocketMessage enum (~187 variants) shared by daemon, client library, and CLI — serde JSON with tag="type"/content="content" adjacent tagging; FromStr = serde_json::from_str; strum Display for logging; optional schemars JSON-schema generation served over the socket itself (SocketSchema command); Newline-delimited JSON framing for requests (BufReader::lines server-side; send_batch joins with '\n'); replies are unframed whole-JSON with termination via socket shutdown — send_query does shutdown(Write) then read_to_string to EOF; Threading: dedicated listener thread wrapped in an outer restart loop (thread::spawn + join; if the accept loop panics it logs 'restarting failed thread' and re-spawns), plus one thread per client connection; all command processing funnels through Arc<Mutex<WindowManager>> (parking_lot), acquired with try_lock_for(Duration::from_secs(1)) so a wedged WM drops commands instead of deadlocking; CLI is a pure 1:1 command mapper: clap-derive SubCommand enum (~170 subcommands) with macro-generated arg structs (gen_enum_subcommand_args! the filter_state_changes option exists precisely because of this firehose; Ctrl-C/stop handling dumps state to temp komorebi.state.json and replays it via ApplyState on next start; stop() also connects to every subscriber socket and shuts it down, then deletes komorebi.sock; Minimal-WM essentials: Essential for a CLI-driven minimal tiling WM (the komorebic model, where whkd/AHK bind hotkeys to CLI invocations): (1) one local listener — a uds_windows UnixListener on a well-known socket path in %LOCALAPPDATA% (or, equally valid and simpler, a loopback-only TcpListener or a named-pipe server; komorebi proves AF_UNIX works fine on Windows but nothing about the design depends on it); (2) a single serde-tagged Command enum shared between daemon and CLI via a small client crate — this one type IS the protocol, the CLI arg surface, and (free with schemars) the documentation; (3) newline-delimited JSON request framing plus reply-then-close for queries — trivially debuggable with any socket tool and avoids inventing a framing protocol; (4) the accept-thread + thread-per-connection + Arc<Mutex<WindowManager>> funnel with a bounded lock wait; (5) a thin clap CLI where each subcommand constructs one enum variant and calls send_message/send_query; (6) the AllowSetForegroundWindow/foreground-lock-timeout startup dance, without which IPC-driven focus commands silently fail; (7) stale-socket unlink before bind and socket cleanup on stop. A no-console wrapper binary (or building the CLI with windows_subsystem="windows") is practically essential too, or every hotkey flashes a console. Optional polish: the TCP remote-control listener, the entire pub/sub notification system (both UDS and named-pipe flavors, SubscribeOptions filtering, full-state broadcasting) — only needed once you want status bars or external integrations; schema-generation commands; batch sends; Hotwatch config hot-reload; state dump/ApplyState restart persistence; process-management subcommands (start/stop/kill via PowerShell); and the ~150 long-tail commands (borders, stackbars, animations, transparency, per-workspace rules). A minimal WM needs perhaps 25-30 verbs: focus/move/stack/resize in 4 directions, workspace focus/send, layout change, retile, toggle-float/monocle/pause, state/query, stop. Note the alternative: built-in hotkeys (RegisterHotKey in the daemon) would eliminate the CLI+socket+wrapper machinery entirely, at the cost of config-driven rebinding flexibility — komorebi's socket design exists precisely to keep keybindings out of the WM core, and it also gets you scriptability (any language can drive the WM) for free.

## Configuration and rules (komorebi.json static config, window matching rules, application-specific configurations, hot-reload)
komorebi's entire user-facing configuration is one serde struct, `StaticConfig` (komorebi/src/static_config.rs), deserialized from komorebi.json. Every field is `Option<T>` so any subset can be specified; old field names are kept alive via `#[serde(alias)]` (e.g. `float_rules` -> `ignore_rules`, `active_window_border*` -> `border*`) and helper fns print deprecation/EOL warnings by raw substring scan of the file. The shape covers: global behaviour knobs (window_container_behaviour Create/Append, float_override, floating_layer_behaviour, four Placement fields, cross_monitor_move_behaviour, cross_boundary_behaviour, monocle_focus_behaviour, unmanaged_window_operation_behaviour, mouse_follows_focus, resize_delta, window_hiding_behaviour Hide/Minimize/Cloak, window_handling_behaviour Sync/Async, min window width/height), visuals (border width/offset/style/implementation/colours, transparency + alpha, stackbar, animation incl. ghost movement, theme, wallpaper), layout defaults (default_workspace_padding, default_container_padding, layout_defaults per layout name, global_work_area_offset), a `monitors: Vec<MonitorConfig>` tree where each monitor has `workspaces: Vec<WorkspaceConfig>` (name, layout, layout_options, threshold-keyed rule maps layout_rules/layout_options_rules/work_area_offset_rules/window_container_behaviour_rules where the key is a container-count threshold, paddings, tile on/off, layout_flip, float_override, initial_workspace_rules and workspace_rules for app->workspace assignment, per-workspace wallpaper), monitor_index_preferences/display_index_preferences for stable monitor ordering, and about ten lists of `MatchingRule` window rules plus `app_specific_configuration_path` (single path or list). All paths in the config are `ResolvedPathBuf` (core/pathext.rs) which expands `%VAR%`, `$Env:VAR`, `$VAR`, `~` and `$HOME` per path component at deserialize time, leaving unresolvable variables literal. Config loading has three phases: `preload()` (read + `apply_globals()` + construct WindowManager + bind komorebi.sock + register file watcher), `postload()` (map monitor configs onto live monitors and populate workspace rules), and `reload()` (both again on change).

Window rules are `MatchingRule` (core/config_generation.rs): either `Simple(IdWithIdentifier)` or `Composite(Vec<IdWithIdentifier>)` where composite is a logical AND of all clauses. An `IdWithIdentifier` is {kind: Exe|Class|Title|Path (core/mod.rs, with lowercase serde aliases), id: String, matching_strategy}. `MatchingStrategy` offers Legacy, Equals, StartsWith, EndsWith, Contains, Regex and the four negations (DoesNotEqual/-StartWith/-EndWith/-Contain). When strategy is omitted it defaults to Legacy, whose semantics differ by kind: Exe/Path use exact equality but Title/Class match if the string starts_with OR ends_with the id. Regex patterns are compiled once at config load into the global `REGEX_IDENTIFIERS: HashMap<String, Regex>` keyed by pattern string. `apply_globals()` pushes each rule list into a corresponding global `Mutex<Vec<MatchingRule>>`: IGNORE_IDENTIFIERS (ignore_rules), MANAGE_IDENTIFIERS (manage_rules), FLOATING_APPLICATIONS, TRAY_AND_MULTI_WINDOW_IDENTIFIERS, LAYERED_WHITELIST, OBJECT_NAME_CHANGE_ON_LAUNCH (+ a separate regex title-ignore list), TRANSPARENCY_BLACKLIST, SLOW_APPLICATION_IDENTIFIERS, NO_TITLEBAR. Consumption happens in window.rs: `should_manage` -> `window_is_eligible` checks hardcoded PERMAIGNORE_CLASSES, then evaluates ignore vs manage (a manage_rules match overrides an ignore_rules match), then the core Win32 heuristic: a window tiles only if it has WS_CAPTION + WS_EX_WINDOWEDGE, lacks WS_EX_DLGMODALFRAME, and lacks WS_EX_LAYERED unless whitelisted via layered_applications or already tracked by the transparency manager — unless force-managed, a WSL2 GUI process, or a remove_titlebar_applications match, which bypass the style heuristic. `should_act()` iterates all rules and returns the last match; slow_application matches cause a literal thread::sleep of slow_application_compensation_time before proceeding.

The ASC (application-specific configuration) system is the community workaround database (github.com/LGUG2Z/komorebi-application-specific-configuration), pointed at by `app_specific_configuration_path`. The modern JSON format (core/asc.rs) is a BTreeMap of app name -> `AscApplicationRules` with eight optional rule lists: ignore (never tile: splash screens, PiP, popups), manage (force-tile windows that fail the style heuristic), floating (manage as floating), transparency_ignore, tray_and_multi_window (apps that minimize/close to tray or spawn multiple windows, so hide events must be handled specially), layered (apps like Steam whose windows carry WS_EX_LAYERED and would otherwise be rejected), object_name_change (rare apps that only announce themselves via EVENT_OBJECT_NAMECHANGE at launch, so that event must be treated as a Show), and slow_application (apps whose event notifications lag, needing a sleep before querying state). A top-level "$schema" key is absorbed by the untagged `AscApplicationRulesOrSchema::Schema(String)` variant. `handle_asc_file` in static_config.rs merges every ASC entry into the same global rule vectors as user rules; it also still parses the legacy YAML format (`ApplicationConfiguration` with `options: [object_name_change|layered|tray_and_multi_window|force|border_overflow]` plus `ignore_identifiers`, alias float_identifiers), and `ApplicationConfigurationGenerator` can emit PowerShell/AutoHotkey scripts of `komorebic.exe` identify-* commands from it — the historical pre-static-config mechanism. `border_overflow` is fully deprecated: it is a no-op in ASC handling and `unreachable!()` in the generator, so that identifier category patches nothing anymore.

Hot-reload works by loopback IPC rather than direct mutation: `preload()` registers a Hotwatch (notify/ReadDirectoryChangesW) watcher on komorebi.json; on Modify OR Remove events it connects to the komorebi.sock AF_UNIX socket (uds_windows) and writes `SocketMessage::ReloadStaticConfiguration(path)`, so the reload executes serialized on the main command-processing thread. `reload()`/`postload()` re-map monitor configs to live monitors — first by display_index_preferences (config index -> monitor serial_number_id or device_id string), then first-fit over unclaimed configs — cache preferred configs for currently disconnected displays via monitor_reconciliator::insert_in_monitor_cache (for hot-plug), rebuild WORKSPACE_MATCHING_RULES (cleared and repopulated, with initial_only flag distinguishing initial_workspace_rules from workspace_rules) and call enforce_workspace_rules. Notably `apply_globals()` never clears the identifier vectors (populate_rules only appends unseen rules), so deleting a window rule from komorebi.json and reloading does not un-register it until restart. The reverse direction also exists: `StaticConfig::from(&WindowManager)` serializes runtime state back into a config for `komorebic generate-static-config`.
Windows APIs: AF_UNIX sockets on Windows via uds_windows (UnixListener/UnixStream on %LOCALAPPDATA%\komorebi\komorebi.sock) — IPC channel used both for komorebic commands and for the hot-reload loopback message; ReadDirectoryChangesW (indirectly, via hotwatch/notify crate) — watching komorebi.json for edits; GetWindowLongPtrW window styles consulted by rule system: WS_CAPTION + WS_THICKFRAME (also toggled by remove_titlebar_applications), WS_EX_WINDOWEDGE (required for eligibility), WS_EX_LAYERED (rejected unless layered_applications whitelisted), WS_EX_DLGMODALFRAME (always rejected); EVENT_OBJECT_NAMECHANGE WinEvent — object_name_change_applications treat this event as a window-Show signal at app launch; a regex title ignore list suppresses false positives from ordinary title changes; DWM cloaking: DwmGetWindowAttribute(DWMWA_CLOAKED) for the is_cloaked eligibility check, and the undocumented SetCloak function for HidingBehaviour::Cloak (vs ShowWindow SW_HIDE / SW_MINIMIZE for the deprecated Hide/Minimize behaviours); SystemParametersInfo active window tracking (via WindowsApi::enable/disable_focus_follows_mouse) for the end-of-life FocusFollowsMouseImplementation::Windows option; GetWindowRect (WindowsApi::window_rect) for minimum_window_width/height eligibility thresholds; Monitor device identification (device_id, serial_number_id from EnumDisplayDevices/DisplayConfig APIs elsewhere) — consumed here by display_index_preferences to pin configs to physical displays

## Ancillary managers (border_manager, monitor_reconciliator, reaper, focus_manager, transparency_manager, stackbar_manager, animation, theme_manager) in komorebi
Komorebi surrounds its core event loop with eight ancillary managers that all follow the same architectural template: a module-level `static CHANNEL: OnceLock<(Sender, Receiver)>` (crossbeam bounded channel, 20-50 slots), a `send_notification()` helper that `try_send`s and logs-and-drops on a full channel, and a `listen_for_notifications(Arc<Mutex<WindowManager>>)` that spawns a dedicated thread running `handle_notifications` in an infinite restart-on-error loop. Each manager thread locks the shared WindowManager, snapshots the state it needs, and acts on the OS. All are started once from main.rs (lines 329-335). This decouples slow/cosmetic OS work (painting borders, alpha fades, monitor re-enumeration) from the latency-sensitive WinEvent processing loop, and makes each concern crash-isolated (a panicking manager thread just restarts).

border_manager draws focus-colored frames. It has two implementations: `BorderImplementation::Windows` simply sets DWMWA_BORDER_COLOR accents on the app windows themselves (cheap, Win11-only, no extra windows); `BorderImplementation::Komorebi` creates one real top-level window per container ("komoborder-{id}" class, WS_EX_TOOLWINDOW|WS_EX_TOPMOST|WS_EX_NOACTIVATE, WS_POPUP), each owned by its own thread running a GetMessage loop, painted with Direct2D (ID2D1HwndRenderTarget, solid brushes per WindowKind: Single/Stack/Monocle/Unfocused/UnfocusedLocked/Floating). The manager thread diff-checks a snapshot of the monitor Ring against the previous notification to skip redundant work, then creates/repositions/destroys borders to mirror the focused workspace of every monitor. Live movement tracking does NOT go through the manager: the WinEvent hook callback (windows_callbacks.rs) forwards EVENT_OBJECT_LOCATIONCHANGE/EVENT_OBJECT_DESTROY directly to the tracked window's border HWND via SendNotifyMessageW, and the border's own WndProc repositions and re-renders itself; SetWindowPos with the tracked hwnd as the insert-after reference keeps the border glued just above its window in the Z-order.

monitor_reconciliator exists because Windows actively fights a WM during display topology changes: when a monitor disconnects (undock, lid close, sleep, DP link flap), the OS minimizes windows, reshuffles them onto surviving monitors, and invalidates HMONITOR handles, which would silently corrupt komorebi's monitor->workspace->container state. It runs two threads: (1) hidden.rs creates an invisible message-only-style window ("komorebi-hidden", WS_DISABLED/WS_EX_NOACTIVATE) on its own message-loop thread that registers for WM_DISPLAYCHANGE (resolution/scaling), WM_SETTINGCHANGE+SPI_SETWORKAREA (work area/taskbar changes), WM_DEVICECHANGE with RegisterDeviceNotificationW for monitor/display-adapter/video-output device interface GUIDs (hotplug arrival/removal), WM_POWERBROADCAST (suspend/resume + lid switch via RegisterPowerSettingNotification GUID_LIDSWITCH_STATE_CHANGE), and WM_WTSSESSION_CHANGE (lock/unlock via WTSRegisterSessionNotification); it translates these into a 7-variant MonitorNotification enum. (2) The consumer thread handles them: WorkAreaChanged/ResolutionScalingChanged re-query MonitorInfo and re-tile if the cached work_area_size/size differ; DisplayConnectionChange re-enumerates displays (win32-display-data crate, with 5 retries at 150ms), matches state monitors to attached devices by serial_number_id or device_id, and reconciles. Removal is debounced: it waits 3 seconds (releasing the WM lock) and re-queries, because Windows fires spurious removal events; if monitors came back it just restores minimized windows. On verified removal it minimizes focused windows on dead monitors (so Windows won't teleport them), snapshots each removed Monitor (full workspace tree) into a MONITOR_CACHE keyed by serial/device id, prunes known_hwnds and workspace rules, and refocuses monitor 0 if needed. On (re)connect, load_monitor_information detects new device ids and the cache is consulted so a re-docked monitor gets its exact workspace layout back (with dead windows retained-out), then retile_all runs twice to shake out DPI jank. It also stamps LAST_DISPLAY_CHANGE_TIMESTAMP so process_event ignores OS-initiated minimize events within a 10-second grace period, and suspends itself between lock/sleep and unlock/resume.

reaper is the garbage collector for dead windows: many windows die without komorebi ever receiving a Destroy/Hide WinEvent (crashed apps, elevated windows, apps that just stop being visible), which would leave ghost entries in the layout. It runs two threads: a poller (find_orphans) that wakes every 20ms and checks every hwnd in HWNDS_CACHE (a mirror of wm.known_hwnds mapping hwnd -> (monitor_idx, workspace_idx), kept in sync by WindowManager::update_known_hwnds) with IsWindow, plus a visibility heuristic (IsWindowVisible) to catch Word's invisible zombie windows; and a consumer thread that receives the orphan batch, locks the WM, removes each window from its recorded workspace via workspace.remove_window, re-tiles only if it was on a focused workspace, notifies the border_manager and IPC subscribers, and persists the surviving hwnd list to komorebi.hwnd.json. The remaining managers are simpler: focus_manager is a trivial thread that focuses a hwnd asynchronously (used post-animation for mouse-follows-focus); transparency_manager walks the state and applies per-window alpha via layered windows (unfocused windows get TRANSPARENCY_ALPHA, focused/monocle/maximized get opaque, with a blacklist); stackbar_manager draws GDI tab bars over stacked containers (one window per container on its own thread, color-keyed layered window, DrawTextW tabs, WM_LBUTTONDOWN switches stack focus); animation is not a channel manager but a thread-per-animation engine (AnimationEngine::animate spawns a thread that ticks a RenderDispatcher at ANIMATION_FPS with easing, keyed cancellation via ANIMATION_MANAGER map, plus DWM-thumbnail "ghost" windows for movement); theme_manager converts Catppuccin/Base16/custom palettes into the atomic color statics consumed by border/stackbar managers and force-refreshes them.

Mechanisms: Uniform manager template: static OnceLock crossbeam bounded channel + send_notification() with lossy try_send + dedicated listener thread wrapping handle_notifications in an infinite restart loop (crash isolation, no supervision tree needed); Shared state is one Arc<Mutex<WindowManager>> (parking_lot); manager threads lock it, snapshot/clone what they need (border_manager clones the whole monitor Ring), then drop the lock before doing OS calls where possible; Configuration knobs are lock-free globals: AtomicI32/AtomicU32/AtomicBool/AtomicCell statics (BORDER_WIDTH, colors, STACKBAR_MODE, TRANSPARENCY_ALPHA, ANIMATION_FPS...) written by config/theme code, read by manager threads; Border diffing: previous monitor-Ring snapshot + previous notification hwnd + pause/layer/pending-move-op edge cases decide whether to skip a notification entirely (avoids re-laying-out borders on every event); Thread-per-native-window: every border, stackbar, ghost host, and the hidden monitor window each own a thread with a Win32 message pump; the creating thread hands the struct back through an mpsc channel; window struct pointer lives in GWLP_USERDATA; Two border state maps: BORDER_STATE (container-id -> Box<Border>) and WINDOWS_BORDERS (tracking hwnd -> container-id), so both container-driven updates and hwnd-driven winevent forwarding can find the border; Border destruction protocol: Box::into_raw so the manager never drops the Border struct (the window's own thread owns it); is_destroying AtomicBool + 10ms sleep to let in-flight D2D renders finish; WM_DESTROY clears GWLP_USERDATA and drops the render target before WM_NCDESTROY; Monitor identity: serial_number_id preferred over device_id (with duplicate-serial detection falling back to device_id) so monitors keep identity across HMONITOR/display-index churn; DISPLAY_INDEX_PREFERENCES let users pin indices; MONITOR_CACHE HashMap<String, Monitor>: full workspace-tree snapshot of every removed monitor, consumed once on reconnect to restore layout exactly (dead/moved windows filtered out via exe() check and known_hwnds); Transient-removal debounce: on apparent monitor removal, release all locks, sleep 3s, re-enumerate; if the count recovered treat it as a spurious event and just restore minimized windows; Grace-period timestamp (LAST_DISPLAY_CHANGE_TIMESTAMP, checked via display_change_in_progress(10s)) so the main event loop ignores OS-initiated SystemMinimizeStart events during display transitions; Reaper split into poller + actor: 20ms IsWindow polling over a mirrored hwnd->(monitor,workspace) cache (HWNDS_CACHE, refreshed wholesale by WindowManager::update_known_hwnds on every state change), batched orphan removal under one WM lock, border refresh only when a focused workspace changed, persisted hwnd list for crash recovery; Animation engine: thread per animation keyed by string, cooperative cancellation counters (init_cancel/latest_cancel_idx so the newest cancel wins), fixed-fps frame loop with easing progress, RenderDispatcher trait so the same engine drives position, transparency, and ghost-thumbnail animations; Theme manager fans out: converts palette to u32s, stores into border/stackbar atomic color statics, then triggers border force-update and stackbar refresh (borders must rebuild D2D brushes on their own threads via WM_UPDATE_BRUSHES)
Gotchas: Windows fires spurious monitor-removal events: a DP monitor can 'disappear' for a moment (link retraining, sleep) and come back; komorebi waits 3 seconds and re-enumerates before believing a removal, and even for spurious ones must restore windows the OS already minimized; On real monitor disconnect Windows tries to move the focused window to another monitor on its own; komorebi preemptively minimizes focused windows on the dying monitor to stop the OS from relocating them; OS-initiated minimizes during display changes are indistinguishable from user minimizes at the WinEvent level; komorebi uses a 10-second wall-clock grace period after any display-change notification to suppress minimize handling (process_event.rs:335); HMONITOR handles and display indices are unstable across hotplug/suspend; stable identity requires the device path/serial from DisplayConfig, and even serial numbers can be duplicated across identical monitors (DUPLICATE_MONITOR_SERIAL_IDS falls back to device_id); display enumeration can transiently fail mid-hotplug: attached_display_devices retries 5 times with 150ms sleeps before giving up, and skips reconciliation entirely if zero devices are returned ('to avoid breaking state'); WINWORD.EXE keeps an invisible WS_EX_LAYERED window alive after closing one of several documents, so IsWindow alone can't detect the zombie; the reaper also reaps invisible windows - but must NOT do that when HidingBehaviour::Hide is active, because komorebi itself makes legitimate windows invisible (reaper.rs:186-199 calls the hack out with an extended rant); Border transparency needs the PowerToys DwmEnableBlurBehindWindow hack with a blur region positioned off-screen (-GetSystemMetrics(SM_CXVIRTUALSCREEN)-8) to remove black pixels around rounded corners; the comment admits nobody knows exactly why the value works; D2D render target must only be touched from the border window's own thread: brush updates are marshalled via a custom WM_UPDATE_BRUSHES message to avoid a data race between the manager thread dropping the old render target and the window thread mid-render; Border Box<Border> must never be dropped normally - destroy_border converts to a raw pointer and lets the window's message-loop thread dispose of it after the window closes (explicit IMPORTANT comment at border_manager/mod.rs:783); WM_DESTROY must clear GWLP_USERDATA and drop the D2D render target before WM_NCDESTROY, or D2D frees its internal HwndPresenter while still referenced; GetForegroundWindow lags behind the actual focus change: SystemForeground winevents arrive before the foreground value updates, so the winevent callback fires an extra border notification once the system has caught up (windows_callbacks.rs:122-130); Refocusing a window after an admin/elevated window leaves the border stuck at Unfocused because WM state is unchanged; the border manager has an explicit edge case checking the notification hwnd's current border kind; EVENT_OBJECT_LOCATIONCHANGE forwarding must filter out WS_CHILD/WS_EX_TOOLWINDOW/WS_EX_NOACTIVATE windows or borders would chase tooltip/child-window move events; WM_SETTINGCHANGE with SPI_SETWORKAREA is the only signal for taskbar auto-hide utilities changing the work area; WM_DISPLAYCHANGE alone misses it; Laptop lid close does not reliably produce device-removal events; komorebi listens for the lid-switch power setting GUID and treats lid transitions as DisplayConnectionChange; Border channel notifications are lossy by design (try_send, drop-on-full) - every consumer re-reads full WM state per notification, so dropped notifications only delay convergence, never corrupt it; Reaper polls at 20ms; the visibility heuristic plus polling means a window that momentarily reports !IsWindowVisible can be reaped incorrectly if hiding behaviour assumptions are violated; retile_all is called twice after monitor changes 'to fix DPI/resolution related jank' - one pass is not enough when per-monitor DPI changes window sizes as they move
Minimal-WM essentials: ESSENTIAL: (1) monitor_reconciliator - a Windows tiling WM that ignores display topology changes corrupts its state the first time a laptop docks/undocks, sleeps, or changes DPI; the minimum viable subset is the hidden message window listening for WM_DISPLAYCHANGE + WM_DEVICECHANGE + WM_POWERBROADCAST resume, re-enumeration with stable device-id matching, work-area/size refresh, and removal/addition of monitors with a debounce; the workspace-cache-restore, session-lock gating, and lid-switch GUID are polish you can add later, but the 'verify removal after 3s' debounce and the minimize-suppression grace period are load-bearing against real OS behavior. (2) reaper - WinEvents genuinely miss window deaths (crashed processes, elevated windows, tray apps), so ghost entries accumulate without a liveness sweep; a minimal version is small: a mirror map of managed hwnds, an IsWindow poll (20ms in komorebi; 100-250ms is fine), and batched removal + retile. STRONGLY RECOMMENDED: border_manager, but in its cheap form - on Windows 11 the DWMWA_BORDER_COLOR 'Windows' implementation gives a focused-window indicator in ~30 lines with no extra windows, threads, or Direct2D; without any indicator a tiling WM is genuinely hard to use. The full komorebi-style D2D overlay-window border system (per-container windows, message pumps, winevent forwarding, destruction protocol) is the single largest source of complexity and gotchas in this list and is entirely skippable polish. SKIPPABLE: focus_manager (only needed as an async helper for animations; a minimal WM focuses synchronously), transparency_manager (pure eye candy; also forces you into layered-window alpha management), stackbar_manager (only meaningful if you implement container stacking with tabs, and explicitly tied to the no-bar-UX komorebi wants; you said no bar), animation/* (pure polish, and its thread-per-animation + cancellation + ghost-thumbnail machinery leaks complexity into window.rs and border code), theme_manager (config sugar over border/stackbar colors; pointless without the komorebi border implementation). Architecturally, the one pattern worth copying wholesale even for a minimal WM is the channel + dedicated-thread + restart-loop template and the rule that consumers re-derive everything from a state snapshot per notification (lossy channels stay safe); the one pattern to avoid copying is per-window native message-pump threads unless you actually build overlay borders.
